## 已核实的现状
1. backend/mcp_server/agents/chat_agent.py::run_chat_turn 仅调用 chat_agent；max_turns=15，timeout=120 秒。没有多 Agent 深度分析接入。
2. frontend/lib/api.ts 的聊天消息和预设接口 timeout=150000 毫秒。
3. backend/app/config.py 中 llm_timeout 默认120秒；openai_loop 的单请求超时为 min(settings.llm_timeout or timeout, timeout)。仅改 LLM_TIMEOUT 不能突破聊天循环120秒上限。
4. OpenAI 循环在轮次边界检查总时间，SDK 在收到消息后检查；不是覆盖所有 await 的硬截止。过拟合工具自己的 HTTP timeout=300 秒，因此工具可能超出外层名义预算。
5. agent_chat.py 在 Agent 完成后才保存用户/助手消息。以 Agent error: 开头的失败会在落库前返回502；只检查文本前缀，可能忽略结构化 error。
6. OpenAI 工具日志保存工具名/参数/执行标志，不保存完整返回值；SDK 只收集文本及 ToolUseBlock，没有完整工具结果配对。
7. 原多 Agent 编排有交易工具，Reflector 有 apply_strategy 等写操作。聊天深度分析不能直接调用原 run_multi_agent。
8. 用户明确报错为 `Agent loop terminated (timeout/max_turns)`。它来自 OpenAI兼容循环，不是 Axios 的浏览器超时文案。日志存在120秒累计超时、4轮20工具、142.8秒退出的候选记录；无run_id，不能严格绑定用户请求。

## 本次报错专项分析（V2修订）
- 源码：`/Users/liumou/PycharmProjects/ai-trading-agent/backend/mcp_server/agents/openai_loop.py:220-230,343-378`。
- 两个分支都会将success置false：累计时间超过timeout，或turns达到max_turns而尚未形成最终答复。该文案本身不能区分两者。
- turns是在一次模型响应返回后加一，不是工具调用数，也不是用户聊天消息数。一轮可调用多个工具。
- 带tool_calls的助手文本只进入messages，未加入text_parts。达到预算退出时，即使中途模型说过话，也可能输出这条兜底文案；不能据此认定模型全程没有文本。
- 当前聊天固定120秒/15轮。日志`/Users/liumou/PycharmProjects/ai-trading-agent/backend/logs/bot.log:39600-39601`记录2026-09-17 20:07:43+08:00 cumulative timeout after 120s；4 turns,20 tools,142.8s。该记录明确不是15轮耗尽。
- 邻近工具记录涉及行情、指标、账户、历史、波动预测、VaR及风险计算；缺少完整结束事件和请求关联，不能把某一时间间隔直接归因某工具或模型，不确认单一慢点。
- 总时限仅在while开头检查，模型请求、自动重试与串行工具期间可超预算；若模型在超预算后直接返回最终文本，甚至可能绕过下一轮检查。必须覆盖每个await及最终状态判定。
- 路由`/Users/liumou/PycharmProjects/ai-trading-agent/backend/app/api/routes/agent_chat.py:173-188`仅识别 `Agent error:` 前缀，忽略result.error；该兜底文案不匹配前缀，按现有代码可作为普通回复落库并HTTP200返回，造成失败伪装成功。
- 结论：本次优先处理后端循环预算/终态传播，而非把问题首先归因前端150秒。只加前端等待或只提高轮数都不够。
- 原始事件日志仅作证据，未发真实模型/工具请求复现，未修改服务配置。

## 建议实施阶段
### P1 优先修复循环终止、预算与失败留痕（批准后执行）
- 聊天总预算建议600秒，单模型请求180秒，普通工具60秒，重计算工具300秒；均受总剩余时间限制。建议新增聊天专属配置，不仅修改全局LLM_TIMEOUT。
- max_turns可配置，首版默认保持15：本次候选记录仅4轮退出，无证据支持盲目加大轮数。临近上限时预留最后一轮仅做总结（禁用工具），明确总结未完成/数据不足，不能保证一定有完整报告。
- 增加按预算收敛：总预算中预留收尾时间；接近截止时停止发起新重计算，不得为“最后总结”无限延长总期限。
- 临时同步模式前端等待660秒，仅限聊天接口；代理若存在须核对其限制，不全局延长普通API。
- 新配置须校验范围；按单次run保存配置快照；不更改自动交易循环的默认预算。
- 单调时钟+外层硬截止，重试消耗同一预算；修复max_retries=0被 `or 2` 覆盖的语义。取消等待不等于远端计算停止，重工具须记录此限制并避免自动重复提交。
- 定义统一终态与reason_code：completed / failed / timed_out / incomplete / cancelled；明确区分total_timeout、max_turns、llm_request_timeout、tool_timeout、provider_error、empty_response、circuit_open。不以自然语言前缀判断成功。
- 保留每轮公开助手文本和工具输入输出，partial_response与final_response分离；超时/轮数耗尽不可变成成功报告。
- 先存用户消息及run，再调用模型；失败也保存状态及已产生内容。同步超时返回结构化504，轮数耗尽返回显式incomplete状态；后台查询HTTP200只代表查询成功，任务终态独立显示。
- 前端显示中文具体原因、已耗时/轮数、部分结果和重试入口，错误与有效报告视觉区分。
- 隔离回归必须覆盖：4轮耗时超过120秒、15轮未完成但时间未超、15轮内正常完成、工具超剩余预算、带工具助手文本保留、耗尽前禁用工具总结、摘要失败、重试预算、无文本/空choices、路由不吞error、失败先落库。采用mock与可控时钟，不靠真实等待600秒。
- P1通过后再推进P2后台化与P3多专家；不以扩容超时掩盖实际慢点。

- 优先评估现有 Runner/Redis 队列的隔离、重启恢复与确认语义，不假设可直接复用。
